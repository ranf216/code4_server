## Part A — Previously blocked (✅ resolved)

### ~~Q1. Client recipient of standalone reports~~ ✅ Resolved — Implemented

**Decision:** Optional resident selection (`client_user_id`) on creation; default to community-wide client visibility upon delivery.

**Implemented:**
- `Report/create_report` accepts optional `client_user_id` for standalone reports (rejected with `ERR_INVALID_API_PARAM` on call-linked reports, which keep the call creator as recipient). Must be an active resident of the report community, otherwise `ERR_REPORT_INVALID_CLIENT` (rc 740).
- Residents see delivered reports addressed to them **or** delivered reports with no recipient (`IRP_CLIENT_USR_ID IS NULL`) in their community — in `get_reports_list`, `get_report` and `get_report_for_client`. This also covers call-linked reports whose call has no resident creator (Q13).
- Client views and the PDF contain only client-included sections; internal sections are stripped server-side.

---

### ~~Q2. Content of the watermarked PDF~~ ✅ Resolved — Implemented

**Decision:** Semi-transparent diagonal watermark with standard audit header/footer.

**Implemented** (`$ReportPdf`):
- Diagonal `"CONFIDENTIAL – AUTHORISED USE ONLY"` watermark on every page at 15% opacity.
- Running header on every page: community name | report title | Report ID.
- Footer on every page: delivery date/time, `"Generated by Code4 Axis Security Operations"`, page numbers (template setting) and the template confidentiality footer when set.
- Texts and opacity are configurable in `runtime_config.js`: `REPORT_PDF_WATERMARK_TEXT`, `REPORT_PDF_WATERMARK_OPACITY`, `REPORT_PDF_GENERATED_BY_TEXT`.
- Manager notes and internal sections are omitted (see Q21 for section inclusion).

---

### ~~Q3. POI "Report Encounter" linking~~ ✅ Resolved — Implemented

**Decision:** Option (b) — direct POI link (`IRP_POI_ID`) and field mapping.

**Implemented:**
- New column `incident_report.IRP_POI_ID` (nullable FK to `poi_record`) — `db/db.sql` + `ALTER TABLE` appended to `db/UpgradeDB.sql`.
- `Report/create_report` accepts `poi_id` (validated through `POI/get_poi_record`, i.e. active and assigned to the officer's community; otherwise `ERR_REPORT_INVALID_POI`, rc 741) plus optional `latitude`, `longitude`, `location_address` for the officer's current position (falls back to the officer's latest `gps_log` point).
- Pre-population: `incident_type` ← POI record type, `incident_description` ← subject name, known aliases and POI Record ID, `incident_location` ← officer's current location.
- `POI/get_poi_record` now returns `related_reports` alongside `related_incidents` (calls).

### Q22. Report Encounter details (follow-up to Q3)

**Implemented:**
1. `incident_type` receives the record type **display name** (`Person of Interest`, `Trespass Order`, `Metro Red Card`) rather than the key, consistent with call-linked reports (which use category / service type names).
2. When both `call_id` and `poi_id` are supplied, call values take precedence; POI values only fill fields the call left empty.
3. POI-prefilled `incident_type` and `incident_location` are locked (Q10 rule); `incident_description` stays editable.
4. `related_reports` visibility in `POI/get_poi_record`: admins see all non-draft linked reports; officers see only their own linked reports (the only reports they can open).

### Q18. Technical notes (for information — no answer required unless you disagree)

1. **Column prefix:** Report Template Q3 referred to `incident_report.RPT_CONTENT_SNAPSHOT`, but the `RPT_` prefix belongs to `report_template`. The report tables use `IRP_` / `IRS_` / `IRA_` / `IRH_` (snapshot column: `IRP_CONTENT_SNAPSHOT`).

4. **Additional endpoints:** `start_review`, `release_review` and `get_report_metadata` were added to the API list.

6. **DRY follow-up:** `$Funcs.getFileNamesByIds()` and `$Funcs.getCommunityName()` were added; `poi.js`, `task.js`, `asset.js`, `route.js` and `shift.js` still contain local equivalents that could be switched to the shared helpers.
